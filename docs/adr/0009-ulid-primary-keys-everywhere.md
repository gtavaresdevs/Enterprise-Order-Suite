# ADR-0009: ULID primary keys on every table, pre-launch Flyway re-baseline, human order number
- Status: Accepted
- Date: 2026-09-29
- Decided by: Gabriel (accepted Claude's proposal; Q-03 row 3.11, 2026-09-29). Decided later (Decision 6): Gabriel, register answers of 2026-10-01
- Supersedes: legacy D9 `id-type` ("backend keeps int64; the frontend adapts", `2026-09-24-restaurant-ops-phase-0-foundation-design.md` L82, L91-106) and the matching resolution in manifest 0.4.0 `x-open-decisions` `id-type`; the ai-ready R12 wording "no IDENTITY ids on offline-capable entities".
- Related: ADR-0000, ADR-0003, ADR-0004, ADR-0007, ADR-0008, ADR-0010, ADR-0019

MASTER-PLAN §4 (L67) resolves it as a proposal: ULID keys on every table, "one pattern agents can't get wrong; no data to migrate".
- D-8 (MASTER-PLAN L41, ADR-0008): no production data; schema and API can be reshaped freely.
- The migration rules forbid a re-baseline as written:
  - `enterprise-order-suite/.claude/skills/flyway-migrations/SKILL.md` L26-30: "## Never edit an applied migration ... The fix is always a **new** version, never a correction in place."
  - `enterprise-order-suite/.claude/agents/flyway-migration-author.md` L18: "**Never edit an applied migration.** Flyway checksums them. Write a new version."

## Decision
Accepted (Gabriel, 2026-09-29; Q-03 row 3.11, "3 Yes"). Proposed by Claude in MASTER-PLAN §4 L67.

1. **Every table's primary key is a ULID.** No table uses `IDENTITY`, `SERIAL`/`BIGSERIAL` or a database sequence for its primary key. Foreign keys reference ULIDs. Join, token, history and audit tables included.
2. **The application generates ids**, not the database. Offline-capable entities (orders, order lines) may receive their ULID from the client (ADR-0003); the server accepts a client-supplied id only where the relevant contract says so.
3. **Flyway is re-baselined once before launch.** V1-V21 are replaced by a new baseline that creates the target schema (ULID keys, `restaurant_id` on tenant-owned tables, missing foreign keys). Planned timing (Claude's plan, not part of Q-03 row 3.11): Build 1 (Tenant foundation), which already touches every table (pm-tool L123). Later build steps add ordinary incremental versions. A second squash before launch is allowed, not required.
4. **The re-baseline window closes at launch**, meaning the first time any environment holds data that must be kept (first real restaurant). After that, "never edit an applied migration" applies without exception. Launch means the first pilot restaurant (Q-32 a, 2026-10-01); no pilot is planned yet (Q-23 b).
5. **Human order number.** Each order also gets a short human number for display and tracking. It is generated by the server (cloud-only this run), unique per restaurant (`restaurant_id` + number), never supplied by the client, never a primary or foreign key. Its format: a running number per restaurant (#1, #2, ...), Q-50 a (2026-10-01); the Order Core contract records it.
6. **Decided later** (Gabriel's register answers, 2026-10-01; the API conventions, Menu and Storefront contracts record the detail):
   - Q-35 a: a ULID is stored and sent as `char(26)` Crockford Base32 in the database, logs and API alike.
   - Q-46 a: each menu category has a ULID on the wire, and items reference it (supersedes legacy D11's name-based wire contract, ADR-0000).
   - Q-69 a: public order tracking: the confirmation link carries the order ULID; a manual lookup needs order number + phone; rate-limited; no list endpoint.

## Consequences
- Before or in the same commit as the re-baseline, agents amend:
  - `flyway-migrations/SKILL.md` L26-30: add the pre-launch exception (one dedicated, reviewed change; only while no environment holds data to keep) and state that the rule is absolute after launch.
  - `flyway-migration-author.md` L18: same amendment.
  - Same pass: `SKILL.md` L24 says the highest version is V19 (actual: V21), and L73-74 points to `docs/contracts/` for target enum names (retired by ADR-0010).
- `BaseEntity.id` changes from `Long` to a ULID type; repository generics, DTOs, mappers, path parameters and tests change with it. `PasswordResetToken` and `PasswordHistory` drop their own `IDENTITY` declarations.
- Every local database is dropped and recreated after the re-baseline. Testcontainers databases are fresh anyway.
- The frontend id type becomes `string` everywhere. This reverses D9's frontend consequence (`id: number`, phase-0 design L104-106).
- Order creation retries become idempotent on the order ULID (ADR-0003, ADR-0004).
- The baseline adds the foreign keys missing today: `order_items.product_id` (V11) and `order_history.order_id` (V12).
- A test or ArchUnit rule forbidding `GenerationType.IDENTITY` may land with the first code it guards (MASTER-PLAN §4 L64); it is not a readiness-gate item.
- Agents must never:
  - add a sequence-backed or `IDENTITY` primary key;
  - let the client supply the human order number;
  - use the human order number as a key or foreign key;
  - edit an applied migration outside the single re-baseline defined here, or after launch.
