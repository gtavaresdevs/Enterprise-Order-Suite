# Glossary

- Status: Draft (seed, S2)
- Updated: 2026-09-29
- Maintained by: Claude. A contested term is settled only by the contract or ADR named in its row, never here first.
- Related: ADR-0001, ADR-0002, ADR-0003, ADR-0004, ADR-0005, ADR-0009, ADR-0012, ADR-0014; `planning/open-questions.md`

How to read the Status column:
- **Accepted (ADR-NNNN)**: decided; use the term as defined.
- **Open -> decided in <contract> (Q-xx)**: do not pick a value or a name in code, API or docs before that contract settles it. Recommendations quoted here are Claude's proposals, not decisions.
- "Code/API" names are English. PT-BR is UI copy only (section 3).

## 1. Domain terms

| Term | Meaning | Status |
|---|---|---|
| Restaurant / tenant | The restaurant is the tenant. One deployment and one database serve every restaurant. Restaurant-owned data carries the restaurant id and every read and write is scoped to the caller's restaurant; a missing restaurant context fails closed. | Accepted (ADR-0001). Isolation mechanism: Open -> decided in Tenancy & Identity contract (Q-25). One tenant = one location or chains: Open -> Tenancy & Identity contract (Q-22). |
| Platform admin vs restaurant roles | Today: global roles `SUPER_ADMIN` > `ADMIN` > `USER` and an env-seeded root `SUPER_ADMIN`, deployment-wide. Target role model is not decided. Recommendation (Q-17 a): a platform admin separate from per-restaurant owner, manager and staff. Never assume the legacy mapping `SUPER_ADMIN` = owner (ADR-0001). | Open -> decided in Tenancy & Identity contract (Q-17 roles, Q-18 platform-admin access, Q-16 one restaurant or many per user). |
| Order Core (Restaurant Operational Core) | The one Order model (with channel and source) and the one Menu per restaurant that every interface consumes through application services. Adapters (controllers, `/public/*`, a future Edge or marketplace) authenticate, map input and set their own identifying fields; they hold no business rules. The frontend is the first consumer. | Accepted (ADR-0002). Class and service names: fixed by the Order Core contract. |
| Channel | How an order is served. Architecture §7 values: `DINE_IN`, `TAKEAWAY`, `DELIVERY`. | Concept Accepted (ADR-0002; the wording is Claude's reading of §7, for confirmation). Value set and legacy mapping: Open -> decided in Order Core contract (Q-49). Wire casing: Open -> API conventions (Q-34). |
| Source | The interface that created an order. Architecture §7 values: `WAITER`, `POS`, `QR`, `TABLET`, `STOREFRONT`, `FUTURE_MARKETPLACE`. Set by the server-side adapter, never from client input (ADR-0002). | Same as Channel (ADR-0002; Q-49, Q-34). Staff-taken phone orders have no source in §7 (Q-49). |
| Menu item vs Product (legacy) | Menu item (`MenuItem`): an item on the restaurant's menu (frontend and manifest term). Product: the legacy backend B2B entity behind `/products` (with stock), replaced, not evolved (ADR-0008); the architecture also lists "Product" and "Items". Whether a separate catalog Product exists: recommendation (Q-43 a) is "the same thing this run, `MenuItem` in code and API". | Open -> decided in Menu contract (Q-43). |
| Modifier / Option | Choices a customer makes on an item. Today: sizes (pick one) and add-ons (with a max quantity). Architecture §8 lists "Modifiers" and "Options" under Menu. Recommendation (Q-41 b): option groups with required, min, max and a price per option. | Open -> decided in Menu contract (Q-41). |
| Table | A restaurant table: a name and a QR code, kept as a settings list with no floor or occupancy view (ADR-0000 FS-09, Kept). | Tables as a settings list: Kept per ADR-0000 FS-09 (ADR-0000 is Proposed; acceptance Q-05). A minimal Table in Order Core this run: Open -> decided in Order Core contract (Q-53). QR code generation: Q-63. QR/table self-ordering: Later (ADR-0007). |
| Customer | The person who places an order. Today anonymous: name and phone captured on each order, no account (legacy FS-03). Architecture §1 lists a Customer entity. | Open -> decided in Order Core contract (Q-51 record vs snapshot). Retention (LGPD): Q-52. |
| Human order number | Short number shown to staff and customers for display and tracking. Server-generated, unique per restaurant, never client-supplied, never a key. | Accepted (ADR-0009). Format: Open -> decided in Order Core contract (Q-50). Tracking lookup: Q-69. |
| ULID | The primary key of every table; generated by the application (orders and order lines may get it from the client). | Accepted (ADR-0009, ADR-0003 C1). Column type and wire format: Open -> API conventions (Q-35). |
| Edge (Restaurant Edge) | A local operational node at one restaurant that keeps orders working when the Internet is down (architecture §2, §12). Optional; not built this run; built only for a restaurant with poor signal. Constraints C1-C6 bind the core now. | Accepted (ADR-0003). What triggers building it: Q-80. |
| Offline Order Queue | The Edge component that holds orders (never payments) until they reach the cloud. Renamed from the architecture's "Offline Transaction Queue". Not built this run. Without an Edge, the app keeps unsent orders on the device and retries them with the same client-generated order id (ADR-0004). | Accepted (ADR-0004 decision 5). Architecture text change: amendment A-08, pending Q-04. Retry mechanism details: Q-38; connection-lost behavior: Q-60. |
| `businessDate` | The restaurant-local calendar date of an order, stamped by the server once at creation in the restaurant's IANA timezone and never recomputed. `createdAt` stays a UTC instant (legacy D15, kept). Not built. | Open -> decided in Order Core contract (legacy D10, pending re-examination, ADR-0000). Timezone source: Q-28; Brazil-only defaults: Q-21. |
| 86 / availability | "86" (kitchen slang): the item is unavailable. The frontend 86 toggle sets `available = false`; customer views never show an unavailable item; public endpoints filter `available == true` on the server (`planning/superseded-docs.md` §4 S-1). | 86 toggle: built (frontend, mock data). Keep stock counts or only the toggle: Open -> decided in Menu contract (Q-42). |
| Record-only payment | The app records a payment result (method, amount, who, when) against an order. It never processes, authorizes, captures, refunds or queues a payment; card terminals authorize on their own. Payment status is separate from order status. | Accepted (ADR-0005). Record shape and payment statuses: Open -> Order Core contract (Q-58). When an order is Paid: Q-55. Cancel of a paid order: Q-56. How online customers pay: Storefront contract (Q-65). |
| Storefront | The restaurant's public customer site: menu, cart, checkout, order status. Owner customization is bounded (ADR-0014). | Customization bounds: Accepted (ADR-0014). How it finds its restaurant: Open -> Tenancy & Identity contract (Q-20, slug Q-31). |
| KDS | Kitchen Display System: the kitchen's live view of the one order stream (ADR-0002). Today a public route. | View over Order Core: Accepted (ADR-0002). Sign-in: Open -> Order Core contract (Q-54). Refresh: Q-61. |
| Plan / package | Reserved words. Not used in code or API this run. | Deferred (ADR-0018). Which word means what: Q-78. |
| Draft / Reviewed / Ready | Doc statuses. Only Gabriel sets Reviewed. | Accepted (ADR-0016). Draft and Ready definitions: Q-12 (decided by Claude: a). Reviewed signal: Q-09. |

The target column is MP §5's proposed map (MP §5 "Glossary" bullet) and Q-49 option a, both proposals.

| Legacy term | Proposed new term | Status |
|---|---|---|
| Channel `Online` | source `STOREFRONT` | Open -> decided in Order Core contract (Q-49) |
| Fulfillment `Pickup` | channel `TAKEAWAY` | Open -> decided in Order Core contract (Q-49) |
| Channel `Dine-in` | channel `DINE_IN` | Open -> decided in Order Core contract (Q-49) |
| Fulfillment `Delivery` | channel `DELIVERY` | Open -> decided in Order Core contract (Q-49) |

| `fulfillment` as its own field | folded into `channel` (Q-49 a) or kept separate (Q-49 b) | Open -> decided in Order Core contract (Q-49) |
| Enum casing `Dine-in`, `New` (frontend, manifest) | `DINE_IN`, `NEW` (Q-34 a) | Open -> decided in API conventions (Q-34) |
| Sizes and add-ons | modifiers / options (architecture §8) | Open -> decided in Menu contract (Q-41) |
| `Product` (legacy backend) | `MenuItem` | Open -> decided in Menu contract (Q-43) |

| Roles `SUPER_ADMIN` / `ADMIN` / `USER` (legacy mapping owner / manager / staff, FS-01, superseded) | platform admin + per-restaurant roles (Q-17 a) | Open -> decided in Tenancy & Identity contract (Q-17, Q-18) |

| Payment status `Paid`, `Pending`, `PayLater` | `UNPAID`, `PAID`, `REFUNDED` (Q-58 a) | Open -> decided in Order Core contract (Q-58, Q-55) |
| Anonymous customer (name + phone per order) | snapshot on the order or a per-restaurant Customer record | Open -> decided in Order Core contract (Q-51) |
| Integer ids (`Long`, `IDENTITY`, legacy D9) | ULID string ids | Accepted (ADR-0009) |

| "Offline Transaction Queue" (architecture §12) | "Offline Order Queue" | Accepted (ADR-0004); architecture text pending Q-04 |
| "Payment Device Gateway" (architecture §12) | removed; no payment queue | Accepted (ADR-0005, ADR-0003 C5); architecture text pending Q-04 |
| Restaurant settings in `PreferencesState` / `localStorage` | typed backend-owned restaurant settings | Accepted (ADR-0014). Which settings are restaurant vs user: Q-27 |

## 3. PT-BR UI vocabulary

Rules (FE `order-ui/docs/superpowers/specs/2026-09-15-core-package-br-i18n-ux-design.md`):
- English keys are canonical and the fallback (L80).
- Translation is presentation only: API values, enums, permission ids, route paths and domain types stay language-neutral; a label maps from a stable enum value at render time (L85).
- PT-BR terms are product vocabulary, not literal translation (L92-96). UI copy is product content, not docs (ADR-0012).
